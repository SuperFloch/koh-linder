# Koh-Linder — mémoire du projet

## Concept
Jeu narratif inspiré de **Reigns**, qui fait vivre une aventure **Koh-Lanta**. Tout se joue **exclusivement au swipe** (gauche / droite). Surtout narratif, avec quelques notions de RPG et de décisions.

## Stack
Quasar 2 (Vue 3, `@quasar/app-vite`), vue-router (mode hash), `vue2-hammer` + `hammerjs` (swipe). **Cible de déploiement : PWA uniquement.** Electron (`src-electron`) et Cordova (`src-cordova`) ont été supprimés, ainsi que les blocs de config des modes inutilisés (ssr, cordova, capacitor, electron, bex) dans `quasar.config.js`, la dépendance `electron` et les entrées `.gitignore` associées. Le mode PWA de Quasar n'est **pas encore ajouté** (pas de `src-pwa/`) : le bloc `pwa` de `quasar.config.js` est prêt ; il restera à lancer `quasar mode add pwa` et fournir manifest/icônes. Build actuel : SPA (`dist/spa`).
Scripts : `npm run dev` (quasar dev), `npm run build`, `npm run lint`, `npm run format`. Pas de tests.
Dans ce shell (Git Bash via l'outil), éviter les gros heredocs : utiliser l'outil Write pour créer des fichiers.

## Entités du jeu
- **Character** : référence du dictionnaire de personnages (réserve de personnages à **rareté**, `public/content/characters/<id>/infos.json`). Champs : `id`, `name`, `sex` (M/F), `age`, `job`, `rarity`, `unlockCost`, `attributes`, `cards` (cartes propres, mécanique **partiellement implémentée**). Images/cartes propres par personnage : à venir.
- **Rareté** (`Rarity` / `RarityLabel` dans `Character.js`) : `RARE` (Rare), `MYTHIC` (Mythique), `LEGENDARY` (Légendaire). Myriam et Thierry sont Rare, Phil est Mythique, Laurent Légendaire (40 Koh-points, SOC / STR / SWI à 9, INT 1, AGI et OBS 2 ; carte « Éclair de génie » sur un d20 de 18-20 à un jet d'INT d'épreuve individuelle : « Laurent s'écrie : Je pensais être con mais j'le suis paaaas !! », carte **intercalée** : le jet est ensuite résolu normalement). Chaque `infos.json` a un champ `bio` (biographie). Badge `.rarity .rarity-rare|mythic|legendary` (sky / sable / jungle). Un personnage créé par le joueur ou un profil généré a `rarity = null`.
- **`unlockCost`** : coût en Koh-points pour rendre un personnage jouable (0 = jouable d'emblée : Myriam, Thierry ; Phil = 25).
- **Candidate** (extends Character) : Character invoqué en jeu. Porte l'évolution dans la partie (energy, eliminated, isPlayer, team, modifiers, `relations`…).
- **Attribute** (clés identiques aux valeurs) : STR (constitution/endurance), INT, SWI (nage), AGI (agilité/précision), OBS (observation), SOC (social).
- **Card** : unité de narration (voir « Système de cartes »).
- **Team / Camp / TeamColor**, **Condition** : squelettes dans `src/model/`. **Effect** : types implémentés dans `Game.applyEffect`. **GameHistory** (ex-`Token`) : historique des évènements marquants, voir ci-dessous.

## Historique de partie (`src/model/GameHistory.js`)
`GameHistory` (anciennement `Token`) garde la **mémoire des évènements marquants** de la partie (`game.history`). Il servira à créer des **Achievements** et de **journal récapitulatif** en fin de partie.
- Une **entrée** (`HistoryEntry`) = `type` (`HistoryType`), `participants` (**ids** des candidats impliqués, `Candidate.id`), `description` (texte lisible), `day` (jour in-game, `game.currentDay`) et un `data` optionnel pour les achievements (ex. `{ gauge, value, challenge }`).
- **Types** (`HistoryType`) volontairement peu nombreux : toutes les réussites d'épreuve partagent `CHALLENGE_SUCCESS`, tous les échecs `CHALLENGE_FAILURE` ; `GOOD_MOMENT` (bon moment entre candidats, AFF monte), `DISPUTE` (dispute, AFF baisse), `TEAM_SELECTION` (formation des équipes : premiers et derniers choisis), `CAMP_CONTRIBUTION` / `CAMP_FAULT` (vie de camp : contribution remarquée / manquement reproché). Ajouter un type seulement si l'évènement n'est vraiment pas assimilable à un existant.
- **« S'inscrire dans l'historique »** = ajouter une entrée (`game.record(type, participants, description, data)`, participants = candidats ou noms). **Règle permanente : toute action qui change l'AFF ou la REP de plus de 1 (en valeur absolue) s'inscrit dans l'historique** — c'est automatique pour l'effet `RELATION` (`Game.recordRelationChange`) : type par défaut AFF+ → `GOOD_MOMENT`, AFF− → `DISPUTE`, REP+ → `CHALLENGE_SUCCESS`, REP− → `CHALLENGE_FAILURE`, surchargeable par `historyType` / `description` dans l'effet ; `history: false` supprime l'entrée automatique quand l'appelant inscrit lui-même une entrée groupée (ex. un duo). Les changements de 1 ne sont pas inscrits. Une autre action ne s'inscrit dans l'historique que si on le précise.
- Déjà inscrits : salutation du bateau (±2 AFF), classement de la nage (1er et 2e : succès ; avant-dernier et dernier : échec), FireCourse (un `GOOD_MOMENT` par duo, et une entrée par duo 1er / 2e / avant-dernier / dernier).
- API : `add`, `byType(type)`, `involving(candidateId)`, `onDay(day)` ; `Game.getEntityById(id)`.
- Chaque entrée garde la couleur d'équipe de ses participants au moment des faits (`teams`) ; **le journal de débogage masque les entrées de l'équipe adverse** (tous les participants dans l'autre équipe à ce moment-là). Les entrées d'avant la formation des équipes (`NONE`) restent visibles.
- **Journal de débogage** : bouton « Journal (DEBUG) » en bas à gauche de l'écran de jeu (`DebugJournal.vue`, activé par `DEBUG` dans `src/debug.js`, à passer à `false` pour le masquer) ; il ouvre la liste des entrées (jour, type, variation d'AFF / REP, description, participants). Il affiche les valeurs d'AFF / REP : à ne jamais exposer au joueur en version finale.

## Échelle de référence des changements de relation
**Cette échelle fait référence pour toute variation d'AFF ou de REP.** Pour les évènements décrits à l'avenir, **ajouter les changements de relation correspondants même s'ils ne sont pas précisés**, en choisissant la valeur sur cette échelle (et rappel : toute variation de plus de 1 en valeur absolue s'inscrit dans l'historique).

| REP | Niveau | Exemples |
|---|---|---|
| +5 | Performance décisive positive | Victoire d'une épreuve, arriver à faire du feu |
| +4 | Performance mémorable positive | Très bonne récolte exceptionnelle (gros poisson, plante nourrissante…), arriver 2e à une épreuve |
| +3 | Performance admirable positive | Participer avec succès à une activité utile, évènement modérément important |
| +2 | Anecdote remarquable positive | Petit exploit sportif, effort remarqué |
| +1 | Fait positif banal | Étape d'épreuve franchie, tâche de camp faite au juste minimum |
| −1 | Fait négatif banal | Petit raté sportif, piètre résultat de récolte |
| −2 | Erreur reprochable | Raté remarqué, chute en épreuve, manquement à l'entretien du camp |
| −3 | Mauvaise conduite | Anti-sportivité, défaite provoquée, gaspillage de ressources |
| −4 | Incompétence visible | Défaite sportive, piètre performance, vote au conseil déplaisant |
| −5 | Défaite capitale | Dernière place, perte de matériel de survie, vote au conseil regrettable |

| AFF | Niveau | Exemples |
|---|---|---|
| +5 | Souvenir impérissable positif | Victoire collective, partage d'un moment rare |
| +4 | Souvenir marquant positif | Partage d'une récompense de confort, alliance de confiance lors d'un conseil |
| +3 | Souvenir positif | Anecdote heureuse partagée, réussite collective |
| +2 | Moment positif | Petite expérience positive partagée, participation en duo à une épreuve sans défaite |
| +1 | Instant positif | Interaction agréable |
| −1 | Instant négatif | Interaction désagréable |
| −2 | Moment négatif | Léger désaccord, petit accrochage |
| −3 | Souvenir négatif | Dispute, pénalité infligée à l'autre |
| −4 | Souvenir mémorable négatif | Grosse pénalité infligée à l'autre, vote au conseil sans élimination |
| −5 | Souvenir crucial négatif | Vote au conseil qui provoque l'élimination |

- **Classement d'épreuve** : seuls les 1er (+5 REP), 2e (+4), avant-dernier (−4) et dernier (−5) changent la REP (auprès de tous les autres) ; les rangs intermédiaires ne changent rien.
- Vérifié cohérent avec l'existant : salutation ±2 AFF, compagnon de nage +1 AFF / −1 REP, course modérée ratée −1 REP, courte échelle ratée −1 REP (explicite), saut de haie réussi +1 REP (explicite), duo qui termine la FireCourse +3 AFF (réussite collective). Corrigé : le classement de la nage (auparavant +5…+1 / −5…−1 sur 5 rangs) et celui de la FireCourse (auparavant seulement vainqueurs / derniers) suivent maintenant la règle 1er / 2e / avant-dernier / dernier.
- **Aucune équipe au début** : `team = NONE` pour tous ; les équipes sont formées à la fin de la première épreuve (épreuve `TEAM_DRAFT`, voir « Épreuves »). `Team` a `color`, `leader` (nom du chef) et `name` (nom tribal).

## Décisions des non-joueurs (`src/model/Decision.js`)
Un candidat non-joueur qui doit en choisir un autre décide **uniquement d'après ses relations** : ses stats et celles des autres lui sont invisibles. Le score relationnel envers un candidat = **AFF + REP**. La **REP tient lieu de score perçu des stats** : un candidat à 10 en STR qui a raté tous ses jets de force est perçu comme mauvais.
- **Contexte positif** (choix de coéquipier, récompense à octroyer, déclaration du vainqueur) : le **meilleur** score l'emporte. **Contexte négatif** (vote d'élimination au conseil) : le **pire** score l'emporte (`DecisionContext.POSITIVE / NEGATIVE`).
- **Décision individuelle** : un décideur (ex. le **vote au conseil**, le compagnon de nage). **Décision collective** : les scores relationnels de tous les décideurs **s'additionnent** (ex. le **choix des coéquipiers** : toute l'équipe, chef compris, décide).
- À chaque option on ajoute un **d6** : 1 → −3, 2 → −2, 3 → −1, 4 → +1, 5 → +2, 6 → +3 (`rollD6Modifier`). Égalités : la somme des AFF départage, puis le hasard.
- `decide({ deciders, options, context })` est la fonction à utiliser pour **toute** décision de choix d'un candidat par un non-joueur (déjà utilisée par `SwimRace.pickCompanion` et `TeamDraft`). Le conseil (vote) reste à implémenter avec elle.
- `Candidate.relationScore(nom)` / `affection(nom)` lisent sans créer d'entrée.
- **Liste des candidats du joueur** (`sortForPlayer`) : joueur en tête, puis par meilleur score de relation (du point de vue du joueur), AFF en cas d'égalité, puis sexe (priorité au sexe du joueur), puis ordre alphabétique. Seul l'ordre est visible, jamais les valeurs.

## Relations entre candidats (jauges cachées)
Chaque candidat a, **envers chaque autre candidat**, deux jauges **sans aucune limite** (0 = neutre ; elles étaient bornées à ±10, ce n'est plus le cas), stockées dans `Candidate.relations[nomDeLAutre] = { AFF, REP }` (`getRelation`, `changeRelation`) :
- **AFF (affection)** : à quel point l'autre lui est sympathique. Monte après un bon moment passé ensemble, baisse après une dispute.
- **REP (réputation)** : à quel point la compétence/utilité/efficacité de l'autre est reconnue. Baisse quand l'autre rate un mouvement pendant une épreuve, monte quand il offre la victoire. Les actions de la vie de camp (nourriture, feu, cabane) agissent aussi sur la REP.
- Ces valeurs influeront surtout sur les **votes aux conseils** (à implémenter).
- **Règle absolue : ne jamais afficher AFF/REP au joueur** (ni dans la liste des candidats, ni ailleurs), pour qu'il ne puisse pas deviner les résultats des conseils.

## Énergie et vie de camp
- `Candidate.energy` = forme physique, de 0 à 100 (`ENERGY_MAX`), **50 au départ pour tous** (`ENERGY_START`). Elle **diminue quand le candidat agit**, remonte en partie **chaque nuit** et **en mangeant**. La survie est dure : même avec de bonnes récoltes, un bon sommeil et des victoires aux épreuves de confort, la jauge doit globalement baisser. Visible du joueur (barre du haut). **Tout jet de STR ou de SWI coûte 1 énergie** (`Candidate.rollStat`).
- **Vie de camp** : entre les épreuves, les candidats vivent sur une île déserte et dépensent leur énergie pour aider à la survie (implémentée, voir « Vie de camp et cycle jour / nuit »).

## Vie de camp et cycle jour / nuit (`src/model/Time.js`, `src/model/challenges/CampLife.js`)
- **Journée** (`Period`, `Time.js`) : Réveil (1 action) · Matin (2) · Midi (1 repas) · Après-midi (3) · Soir (1 repas) · Nuit (1 action sociale, puis sommeil). `Game.currentDay` (commence à **1**, la partie démarre sur le bateau) et `Game.period`. Chaque candidat a un nombre d'actions limité par période et **doit toutes les dépenser** : la période ne finit que quand le joueur a dépensé les siennes, et chaque non-joueur dépense la sienne à chaque action du joueur.
- **Calendrier** (`CampLife.dayKind`, `DayKind`) : jour 1 = arrivée (Après-midi seulement, 3 actions, après la bannière) ; **jour 2 : vie de camp (survie)** ; **jour 3 : épreuve de confort** ; **jour 4 : épreuve d'immunité + conseil** ; puis le cycle se répète (survie, confort, immunité + conseil) **jusqu'au jour 22** (`lastDay`, 7 conseils, après 7 éliminations), où la vie de camp se termine (`END`). Un jour d'épreuve (confort ou immunité) n'a pas d'action de Matin (une épreuve d'équipe tirée au sort la remplace) ; un jour de conseil n'a pas d'action de Nuit. Les listes explicites `challengeDays` / `councilDays` (paramètres de CAMP_LIFE), si elles sont renseignées, remplacent le cycle (tests). **Les conseils, les éliminations et les votes ne sont pas encore implémentés** : le jour de conseil, la Nuit est simplement sautée.
- **Épreuve d'immunité** : l'équipe gagnante est enregistrée dans `game.immuneTeam` (pour le futur conseil).
- **Récompenses des épreuves de confort en équipe** (`CampLife.applyComfortReward`, ordre fixe, la i-ème épreuve de confort donne la i-ème récompense à l'équipe gagnante ; une récompense indisponible est sautée définitivement ; texte au retour à la vie de camp) : 1) **Kit de pêche** : nouvelle tâche de récolte « Pêche au harpon » (la pêche de l'arbre mène à un choix coquillages / harpon ; jet combiné d20 + SWI et d20 + OBS ≥ 34, réussite 8 nourriture, échec 0 ; +3 REP / −1) ; 2) **Allumette** : feu allumé instantanément (disponible seulement si aucune équipe n'a son feu allumé) ; 3) **Guide local sur la faune** : +4 aux jets d'OBS de la survie (pêche, harpon) ; 4) **Réserve de riz** : +40 nourriture ; 5) **Repas chaud** : +25 énergie pour l'équipe et un plat tiré parmi 20 (`resources/hot_meals.json`) ; 6) **Séjour chez les locaux** : +15 énergie et +3 AFF mutuel ; 7) **Appel à la famille** : +5 énergie et +4 AFF mutuel.
- **Avantage numérique** (`Game.drawSitOut`, `sitOutCard`, `activeMembers`) : quand les équipes sont inégales (éliminations), avant une épreuve d'équipe tirée au sort, l'équipe la plus nombreuse tire au sort ses participants (sac de boules blanches = nombre de candidats de l'équipe adverse, le reste en noires, tirage sans remise = mélange). Les noirs sont écartés (`game.sitOut`, ignoré par `TeamRace.initTeams`) et Denis les annonce sur une carte : « {liste}, vous ne participerez pas à cette épreuve ». Le joueur peut être écarté (il regarde l'épreuve). Pas de tirage en mode DEBUG « épreuve seule ».
- **Tout se joue au swipe** (carte `CHALLENGE_TURN` `camp_05_action`, textes `{campPrompt}` `{campLeft}` `{campRight}`) :
  - **Réveil** — **les non-joueurs jouent AVANT le joueur** (au début de la période) pour savoir qui est levé. Les deux choix font un jet de SOC (seuil 10). *Gauche, se lever tranquillement* : +3 énergie ; jet raté = traîner au lit est mal vu : **−1 REP auprès de tous les coéquipiers déjà levés** (ceux qui ont choisi « directement » avant) ; réussi = rien. *Droite, se lever directement* : on croise au hasard l'un des coéquipiers déjà levés ; jet réussi : **+1 AFF mutuel et +1 nourriture** (quelques racines ramassées ensemble) ; jet raté : il nous salue, aucun changement. Le prompt indique combien de coéquipiers sont déjà debout.
  - **Repas** (midi, soir) — gauche : **festin** (+5 énergie, **+3 énergie de plus si le feu est allumé**, +1 AFF des coéquipiers, consomme **3 nourriture par candidat**) ; droite : **rationner** (+2 énergie, consomme **1 nourriture par candidat**). Sans assez de nourriture : festin → ration ; sans rien : pas d'énergie.
  - Matin / Après-midi — arbre de 3 swipes : *Hors du camp* (g) / *Au camp* (d) → Hors camp : *Récolte* (g) / *Ravitaillement* (d) ; Au camp : *Entretien* (g) / *Social* (d) → Récolte : *Plantes* (g) / *Pêche* (d) ; Ravitaillement : *Eau* (g) / *Bois* (d) ; Entretien : *Cabane* (g) / *Feu* (d) ; Social : *Discussion* (g) / *Pause* (d). Seule la 3e réponse dépense une action. **Une action impossible (cabane sans 2 bois, feu sans 5 bois…) est refusée avec un message, ne dépense rien et ramène au premier choix** (jamais d'impasse).
  - Nuit — gauche : discussion ; droite : pause. **Plus de montant fixe d'énergie de sommeil** : au passage d'un jour à l'autre (même quand la Nuit est remplacée par un conseil), **chaque équipe tire une carte nuit** (`NIGHT_CARDS`, `CampLife.sleep`; une seule pour tous après la réunification) : *Nuit paisible* (40 %) tous +10 énergie ; *Pluie nocturne* +2 énergie (+5 si la cabane est finie), un feu allumé brûle 2 bois de plus, +2 AFF mutuel ; *Invasion d'insectes* +4 énergie ; *Sortie de crabes* +5 énergie et +7 nourriture ; *Tempête* +3 énergie, la cabane retombe à 8/15 (si elle était plus avancée), +2 AFF mutuel ; *Migration de tortues* (5 %) +8 énergie et +3 AFF mutuel. Les quatre cartes sans pourcentage se partagent les 55 % restants (13,75 % chacune). Le joueur voit la carte de son équipe au réveil.
- **Ressources du camp** (par équipe, `Team.camp.resources`, toutes à 0 au départ) : **Eau (max 20)**, **Bois** et **Nourriture** (sans max). Affichées hors épreuves dans un **second header** sous le principal (`CampHeader.vue`) avec l'état du feu (allumé / éteint) et l'avancement de la cabane (`camp.equipements` : `fire` booléen, `cabin` 0 à 15).
- **Cabane** : **15 actions de construction** (`CAMP_CABIN_STEPS`), chacune **consomme 2 bois** ; impossible tant qu'il y a moins de 2 bois. Chaque étape +1 REP auprès des coéquipiers, la dernière +3 (activité utile).
- **Feu** : très difficile. L'action « Feu » réunit **3 aventuriers** (celui qui agit + 2 coéquipiers choisis par `Decision.decide`, positif) pour un **jet joint d'INT à 50** (`Challenge.jointRoll`) ; **chacun dépense 3 énergie**. **Impossible tant qu'il y a moins de 5 bois** dans la réserve (le bois n'est pas consommé à l'allumage). Réussite : feu allumé, +5 REP chacun auprès des coéquipiers et +3 AFF mutuel (deux entrées d'historique groupées). **Allumé, il brûle automatiquement au début de chaque période : 2 bois le Matin, 3 l'Après-midi, 4 la Nuit** ; sans assez de bois **il s'éteint** et il faut le rallumer par le même jet joint. Un message prévient le joueur (consommation, extinction, aide demandée par un coéquipier).
- **Les non-joueurs choisissent AVANT le joueur, à chaque action** (`CampLife.planNpcs`, `planned[nom]`) : le joueur voit sur chaque question « Choix de l'équipe — pêche : Alice, Bob · bois : Cara » (ses coéquipiers seulement) pour décider avec qui passer le temps. Les NPC réalisent ensuite le choix annoncé (après l'action du joueur ; un choix devenu impossible → pause). Une **discussion** du joueur se tient avec un coéquipier qui a lui aussi choisi « discussion » (sinon au hasard). Au réveil, les choix annoncés sont ceux déjà réalisés.
- **Actions** : pêche aux coquillages = d20 + OBS (seuil 10) : réussite +5 nourriture, échec +2 ; plantes = d20 + INT (seuil 15, élevé) : réussite +10, échec +1 ; eau et bois : jamais ratés, +10 chacun ; discussion = d20 + SOC (seuil 10) avec un coéquipier ; pause = +3 énergie.
- **Énergie** : les tâches du matin et de l'après-midi consomment de l'énergie (plantes, pêche, eau, bois : 3 ; étape de cabane : 2 ; discussion : 1 ; pause : +3), en plus du −1 des jets de STR / SWI ; l'allumage du feu coûte 3 à chacun des 3.
- **Relations** (échelle de référence, auprès des coéquipiers) : pêche réussie +2 REP / ratée −1 ; plantes réussies (très bonne récolte) +4 REP / ratées −1 ; eau, bois +1 REP ; cabane +1 (finie +3) ; feu allumé +5 REP et +3 AFF ; discussion réussie +2 AFF mutuel (une entrée `GOOD_MOMENT`) / ratée −1 AFF ; réveil : voir ci-dessus.
- Les non-joueurs choisissent leurs actions selon les besoins du camp (`npcChoice`, tirage pondéré) ; leurs discussions suivent `Decision.decide`.
- **Contenu actuel** (`cards/camp.json`, thème `CAMP`) : Denis « Partez à la découverte de votre campement » → pirogue vers une île déserte (une par équipe) → deux coéquipiers (jamais le joueur) accrochent la bannière pendant qu'un troisième dit « Bienvenue sur l'île des {nom d'équipe} ! » (`PICK_TEAMMATES`, +1 REP aux deux, +1 AFF au troisième, +2 AFF d'équipe) → les sacs sont déposés → vie de camp **jusqu'au jour 22** (voir « Calendrier ») → `END`.
- **Valeurs non précisées, choisies par moi (à ajuster)** : coûts en énergie des tâches, seuils de jet (10 / 15), seuil SOC du réveil (10), +5 d'énergie du festin, +2 de la ration, +1 AFF du festin, REP de la cabane et du feu, seuil du harpon (34), proportions des cartes nuit sans pourcentage, REP du harpon. Le +3 énergie du réveil tranquille s'ajoute à une éventuelle carte de personnage. **L'eau n'est consommée par rien pour l'instant.** Les ressources ne se dégradent pas.

## Épreuves d'équipe (`TeamRace`)
Les deux équipes (rouge / jaune) jouent en même temps : chaque swipe du joueur fait jouer un tour à son équipe **et** à l'équipe adverse ; la première qui remplit l'objectif gagne (`finishRace`). **Minimap : un seul marqueur de progression par équipe, de la couleur de l'équipe** (l'équipe du joueur est repérée par la ligne de statut) via `RaceChallenge.markersAt` (par défaut un avatar par candidat) ; sauf mention contraire dans la description d'une épreuve. Jet d'équipe compact : `TeamRace.teamRoll` (somme des d20 + stat de tous les membres vs seuil = nombre de membres × seuil par membre). **Règle générale des égalités : si le cas d'égalité n'est pas prévu par les règles, le résultat est favorable au joueur ou à son équipe.** Dans `TeamRace`, l'équipe du joueur joue donc en premier dans un tour (`roundOrder()` : elle l'emporte si les deux équipes atteignent l'objectif dans le même tour ; le plongeoir inverse l'ordre car c'est l'échec qui départage). **Compte rendu d'un tour** : `TeamRace.playRound` renvoie des **sections par équipe** (`game.logSections` : `{ color, mine, text }`, équipe du joueur d'abord) que `InGamePage` affiche en blocs séparés, **bordure de la couleur de l'équipe**, **police plus petite pour l'équipe adverse** ; `{raceLog}` n'est plus utilisé par ces épreuves (le texte de la carte ne garde que `{nextStep}`). `TeamRace.combinedRoll(candidat, statA, statB, seuil)` = jet combiné (somme des deux d20 + stat). **Victoire** : +5 AFF mutuel dans l'équipe gagnante (victoire collective, une entrée `GOOD_MOMENT`) et +5 REP auprès de ses coéquipiers pour celui qui apporte la victoire (`CHALLENGE_SUCCESS`) ; rien pour les perdants (les récompenses de confort / d'immunité restent à écrire).
- **Flambeaux** (`TORCHES`, `TorchRelay.js`, `cards/challenges/flambeaux.json`) : chaque équipe porte une lourde caisse de combustible. 18 cases : 2 course avec charge · porte nouée · 2 course · obstacle · 2 course · flambeau (sans test : « {aléatoire} saisit la torche et allume le flambeau de l'équipe ») · retour : 2 course · obstacle · 5 course (la porte devient une course) · mât. Course avec charge : jet joint de STR de **toute l'équipe** (seuil 15 par membre), réussite +2 cases (dans la série), échec +1. Porte nouée : jet joint d'INT des **2 meilleurs en INT** (seuil 30), réussite = passée, sinon on reste. Obstacle : jet joint d'AGI de toute l'équipe (14 par membre), réussite = passé, sinon on reste. **Mât** : le candidat au meilleur AGI grimpe ; le joueur peut se désigner (swipe gauche, sans test) ou laisser le meilleur (droite) ; jet d'AGI difficile (d20 + AGI ≥ 20) répété à chaque tour jusqu'à la réussite → « {candidat} grimpe en haut du mât et embrase la vasque. Une flamme brûle fièrement pour l'équipe des {nom d'équipe} ». Minimap : 18 cases.
- **Élastiques** (`ELASTICS`, `ElasticRace.js`, `cards/challenges/elastiques.json`, force brute) : toute l'équipe attachée au pieu ; **5 bâtons** puis le poignard. Parcours en **7 cases** : départ (le pieu, 0), une case par bâton (1 à 5), la case du poignard (6). Chaque case = jet joint de STR de toute l'équipe, au **seuil croissant jusqu'au poignard** (par membre : 9,5 + 0,9 × n° de case ; élastique de plus en plus tendu). Pour atteindre un bâton, l'équipe **retraverse TOUTES les cases depuis le départ, même celles dont le bâton est déjà pris** (les tests de STR sont refaits à chaque trajet : 1+2+3+4+5 tests pour les bâtons, 6 pour le poignard). **Si un candidat fait 1 au dé : il chute, perd 1 REP auprès de ses coéquipiers et l'équipe ne progresse pas** ; échec : l'équipe reste sur la case ; sur la case de son bâton, « {candidat} attrape le bâton pour son équipe ! » (+2 REP) et **le retour au pieu est instantané, sans aucun test** : le bâton est déposé. Le poignard donne la victoire sans retour. Minimap : 7 colonnes. Durée observée ~39 cartes (les paramètres `sticks`, `basePerMember`, `tensionPerCase` règlent la longueur).
- **Plongée** (`DIVE_RELAY`, `DiveRelay.js`, `cards/challenges/plongee.json`) : 10 colliers sur une corde, relais de plongeurs, un jet de SWI par collier (seuil = ⌈4 + 1,8 × n⌉, de plus en plus dur). Ordre de passage au premier tour : **SWI croissante** ; **personne ne plonge deux fois de suite** ; chacun passe au moins une fois ; quand tous sont passés, n'importe qui peut plonger (pas deux fois de suite) : un non-joueur envoie le meilleur nageur disponible, le joueur choisit au swipe (gauche : plonger lui-même, droite : envoyer le meilleur). Réussite : +1 REP ; échec : −1 REP auprès de ses coéquipiers et le relais continue. La première équipe aux 10 colliers gagne. Minimap : 0 à 10. Les règles du relais (ordre, pas deux fois de suite, chacun au moins une fois, tour libre) sont dans `RelayRace.js`, commun à la plongée et aux poids immergés.
- **Poids immergés** (`SUNKEN_WEIGHTS`, `WeightRelay.js`, `cards/challenges/poids.json`) : chaque équipe a 4 poids coulés à des distances croissantes. **Mêmes règles de relais que la plongée** (`RelayRace`). 5 cases d'eau : la case 0 est le départ où les poids doivent être ramenés, les cases 1 à 4 contiennent chacune un poids. Le nageur nage à la surface vers le poids restant le plus proche (**test de SWI facile**, d20 + SWI ≥ 6 ; échec : il n'avance pas et retente). Arrivé sur la case d'un poids, il passe **en apnée** : **test de SWI difficile** (≥ 14) pour ramener le poids d'une case vers le départ ; réussite : lui et le poids avancent d'une case et il peut retenter ; échec : il ne bouge pas le poids, remonte, **retourne au départ** (tests faciles à chaque case) et passe le relais — le poids garde sa progression pour le suivant. Atteindre le départ, avec ou sans poids, passe le relais. Un swipe = une phase (aller jusqu'au poids d'un coup, puis un test difficile à la fois ; un échec ramène aussitôt le nageur au départ). REP : **chaque poids déplacé d'une case (traction réussie) +1**, aucun bonus pour le dernier (`heroRep: 0`), échec de traction −1. La première équipe aux 4 poids gagne. **Minimap : le marqueur de l'équipe est grisé et teinté de bleu foncé (classe `apnea`) pendant l'apnée** ; **les poids de chaque équipe sont visibles sous forme de boules de la couleur de l'équipe** (`challenge.ballsAt(i)`, optionnel, rendu par `RaceTrack.vue` ; case 0 = poids ramenés ; anneau sable pour l'équipe du joueur). Durée observée ~28 cartes.
- **Poteries** (`POTTERY`, `PotteryRelay.js`, `cards/challenges/poteries.json`) : relais (`RelayRace`). Nager jusqu'à une plateforme (3 cases de nage : test de SWI ≥ 10, réussite 2 cases, échec 1), sauter pour casser une poterie contenant un collier, ramener le collier au départ (même nage) et passer le relais. 7 poteries par équipe, de seuils croissants (24 + 2 × n). Avant le saut, choix entre la **plus difficile encore présente** et la **plus facile** (joueur : swipe droite = difficile, gauche = facile ; non-joueur : vise la plus difficile s'il a de bonnes chances). Saut = **jet combiné** d20 + STR et d20 + AGI, somme comparée au seuil. Échec : **un unique deuxième essai** (choix reposé), puis retour sans collier. REP : poterie la plus difficile cassée **+3**, autre poterie **+1**, **seul le 2e échec coûte −1**, pas de bonus de victoire. Première équipe aux 7 colliers au départ gagne. Un swipe = nage aller d'un coup, puis un saut ; retour d'un coup. Minimap 4 cases. Durée observée ~24 cartes. `TeamRace.finishRace` n'applique le bonus de héros que si `heroRep` ≠ 0.

- **Bobine** (`SPOOL`, `SpoolRace.js`, `cards/challenges/bobine.json`) : chaque équipe désigne un **grimpeur** (premier swipe : gauche = le joueur se désigne, droite = le plus agile ; les NPC prennent le meilleur en AGI). Tour de **5 étages** : monter ou descendre d'un étage = **test combiné** STR + AGI (d20 + STR et d20 + AGI, somme ≥ 30, modéré) ; monté puis redescendu (10 réussites), il **bloque la bobine adverse**. Le reste de l'équipe (sans le grimpeur) porte le coffre sur **17 cases** avec les étapes des flambeaux (`CarrySteps.js`, partagé avec `TORCHES`) : 4 CARRY · DOOR · 2 CARRY · OBSTACLE · 2 CARRY · DOOR · 6 CARRY · arrivée. **Indicateur vertical à gauche de la minimap** : hauteur de chaque grimpeur dans la tour (un point par équipe, `SpoolRace.gauge()` rendu par `RaceTrack.vue` ; API optionnelle `challenge.gauge()` → `{ size, label, items: [{ key, bg, mine, value, title }] }`) ; il n'avance que si sa bobine n'est pas bloquée. Fin : un coffre franchit l'arrivée (victoire), ou les deux bobines sont bloquées (gagne la plus proche de l'arrivée, égalité au hasard). Si le grimpeur a bloqué l'adversaire et que son équipe gagne : **+5 REP** auprès de son équipe et **+3 REP** auprès de l'équipe adverse (historique) ; sinon aucun bonus de victoire. Durée observée ~13 cartes.
- **Fronde** (`SLING`, `SlingRelay.js`, `cards/challenges/fronde.json`) : relais (`RelayRace`), 8 cibles par équipe de seuil croissant (24 + 2,5 × n arrondi), **30 projectiles par équipe** (un passage = un tir, jet combiné d20 + OBS et d20 + AGI). Le tireur vise la cible **la plus proche** (gauche) ou la **plus lointaine** encore présente (droite) ; REP comme les poteries (plus lointaine +3, autre +1, pas de REP négative). Une cible touchée ne compte plus. Gagne l'équipe qui abat les 8 cibles ; munitions épuisées → le plus de cibles abattues ; égalité → **munitions illimitées** et la première équipe qui mène gagne. Après le premier passage de chacun, le joueur tire à chaque fois qu'il le peut (pas deux fois de suite). Durée ~23 cartes.
- **Plongeoir** (`DIVING_BOARD`, `DivingBoard.js`, `cards/challenges/plongeoir.json`) : endurance. Premier swipe : désigner le **suspendu** (le joueur peut se désigner à gauche ; sinon le moins fort en STR). Il n'a aucun test. Les autres font à chaque tour un **jet joint de STR** (somme d20 + STR de tous les porteurs vs 6 × nombre de porteurs, **+1 par porteur à chaque nouveau test**), chaque test = 5 minutes de narration. La première équipe qui rate laisse tomber son suspendu (`{fallenName}`) et l'autre gagne. Aucune REP négative ; pas de bonus de héros. Durée ~14 cartes.
- **Puzzle aquatique** (`WATER_PUZZLE`, `WaterPuzzle.js`, `cards/challenges/puzzle.json`) : puzzle de 5 × 5 pièces par équipe, **0 bien placée au départ**. Premier swipe : désigner le **meneur** (hors de l'eau, seul à voir l'image ; gauche = le joueur, droite = le meilleur OBS + INT). Chaque tour (le compteur de tours = le temps), le meneur fait un **jet combiné d'OBS et d'INT** (d20 + OBS et d20 + INT ≥ 32) : **gauche « réfléchir davantage »** = il passe ce tour, et au tour suivant son jet (résolu automatiquement) reçoit **+5** ; **droite « appliquer la combinaison »** = jet résolu tout de suite. Réussite : **2 pièces** deviennent bien placées ; échec sans réflexion : **1 pièce bien placée devient mal placée** (rien si aucune) ; échec après réflexion : aucun changement. **Chaque tour coûte 1 énergie à tous les candidats non-meneurs** (des deux équipes). Les NPC réfléchissent quand leur espérance est sous le seuil. **Minimap : une grille 5 × 5 par équipe** (`challenge.grids()`, API optionnelle de `RaceTrack.vue` qui remplace la piste), une case de la couleur de l'équipe par pièce bien placée. Fin : meneur vainqueur **+5 REP** auprès de ses coéquipiers et **+3** auprès des adversaires ; meneur perdant **−3** auprès des siens et **−2** auprès des adversaires. Durée observée ~27 cartes.
- Ces trois épreuves ont `heroRep: 0` (le paramètre `heroRep` de `TeamRace` active/désactive le bonus générique +5 du héros).

## Cartes des personnages de la réserve
Les personnages de la réserve ont des **cartes évènement** (`cards` dans `infos.json`). Chaque carte a un **contexte précis** (`context`, un `RollContext`) et une ou plusieurs **valeurs de d20** (`d20` : un **tableau** de valeurs naturelles du dé, avant bonus, ex. `[12, 14, 16, 20]` ; un nombre seul reste accepté) : la carte peut être tirée sur n'importe laquelle de ces valeurs.
- Quand un candidat fait un jet dans un contexte et que la valeur du d20 et le contexte correspondent à l'une de ses cartes, **cette carte remplace la résolution classique du jet** (`Challenge.rollWithCards` → `Game.drawCharacterCard` / `playCharacterCard`). Plusieurs cartes pour le même contexte et la même valeur : **tirage au hasard** parmi elles.
- Format d'une carte : `{ id, name, context, d20, text, effects: [...] }`. Les effets sont des effets normaux ; **`{self}`** désigne le candidat (dans `target`, `about`, `text`…). Le texte accepte les variables du jeu.
- Pour le **joueur**, la carte est intercalée comme une carte de narration (« Continuer ») avant la suite (`Game.pendingCards` / `resumeCard`, `next: "RESUME"`) ; pour un **non-joueur**, ses effets s'appliquent silencieusement. Les changements de relation > 1 qu'une carte provoque s'inscrivent dans l'historique comme tout effet `RELATION`.
- **Contextes branchés** (`RollContext`) : `WAKE` (jet de SOC du réveil, les deux choix), `FISH`, `PLANTS`, `TALK` (vie de camp), `RUN` et `HURDLE` (étapes individuelles de course), `INDIVIDUAL_INT` (jet d'INT d'une épreuve individuelle : le feu du parcours, via `Challenge.jointRoll(members, stats, seuil, contexte)` dont la carte, si elle REMPLACE, fait réussir le jet). Pas encore branchés : plongeon et nage, cartes DICE (à ajouter au fil des besoins).
- **Deux modes de carte** (`mode` dans `cards[]`, `CardMode` de `Character.js`) : `REPLACE` (défaut, ex. la méditation de Thierry) = la carte remplace totalement l'évènement ; `INSERT` (ex. l'éclair de génie de Laurent) = la carte s'intercale entre le jet et sa résolution : ses effets s'appliquent et elle est montrée au joueur, puis le jet se résout normalement avec son résultat inchangé (`rollWithCards` ne renvoie `card` que pour REPLACE et expose `inserted` sinon ; `jointRoll` ne force la réussite que pour REPLACE).
- **La carte (REPLACE) remplace TOTALEMENT l'évènement** (pas seulement le test) : au réveil, ni l'énergie du réveil tranquille, ni le salut, ni la pénalité, ni le statut de lève-tôt ne s'appliquent. (Le coût en énergie d'une tâche du matin / de l'après-midi reste payé : l'action est dépensée.)
- Exemple : Thierry (`thierry_2012`) a la carte « Méditation solitaire » : au réveil, sur un d20 naturel de **12, 14, 16 ou 20**, il médite (+5 énergie) au lieu de saluer les gens réveillés.

## Déroulé d'une partie
1. Choix du personnage à incarner : le **créateur de personnage** (première option) ou un personnage de la réserve **débloqué** (voir « Sélection, Koh-points et galerie »).
2. Constitution du casting (`src/model/CandidateGenerator.js`) : 20 candidats au total = le joueur + `reserveCharacterCount` (1 par défaut) autre(s) personnage(s) de la réserve (Rare/Mythique/Légendaire, débloqués ou non, hors personnage du joueur) + profils aléatoires (prénom selon le sexe, sexe, métier accordé, âge, attributs). Le nombre de personnages de la réserve par partie pourra être augmenté avec les points gagnés. **Aucun doublon de prénom** parmi les 20 (comparaison insensible à la casse, joueur et personnages de la réserve inclus ; un personnage dont le prénom est déjà pris n'est pas tiré). **Toujours autant d'hommes que de femmes** (10 M + 10 F ; un personnage de la réserve qui ferait dépasser la moitié d'un sexe n'est pas tiré). Cet équilibre est indispensable à l'épreuve des binômes mixtes.
3. Déroulé des évènements ; élimination 1 par 1. Si le joueur est éliminé, la partie est terminée.
4. Jour 40 : il ne reste qu'un Candidat, déclaré vainqueur (`GAME_DEFAULT_DURATION = 40`).
5. Fin de partie : **1 Koh-point par jour de survie** (`Game.kohPointsEarned` = `currentDay`), dépensables dans la galerie pour débloquer des Personnages avec de meilleures stats. (`currentDay` commence à 1 ; il avance quand la vie de camp passe au jour suivant. Le contenu actuel va jusqu'au jour 22 : 22 Koh-points.)

## Sélection, Koh-points et galerie
- **Profil persistant** (`src/content/ProfileStore.js`, `localStorage` clé `kohlinder.profile`, tolérant aux erreurs de stockage) : `{ kohPoints, unlockedIds }`. `isUnlocked` = coût 0 ou id débloqué ; `unlockCharacter` débite les Koh-points ; `addKohPoints` crédite en fin de partie. Le profil est possédé par `IndexPage`.
- **Menu principal** : affiche le solde de Koh-points, boutons Nouvelle partie / Charger partie / **Aventuriers** / Succès / Quitter, lien vers l'éditeur.
- **Galerie « Aventuriers »** (`components/charGallery/CharGalleryPage.vue`) : **grille** de tuiles (avatar, nom, et « Jouable » ou bouton avec le prix en Koh-points, désactivé s'il manque des points) ; la **rareté se lit à la bordure de l'avatar** (Rare bleu, Mythique violet, Légendaire or). Au clic sur un aventurier jouable, une **modale** affiche la fiche complète (rareté, métier, âge, biographie `bio`, stats). Solde de Koh-points en haut. Phil coûte 25, Laurent 40.
- **Sélection de personnage** (`CharSelectionPage.vue`) : carrousel dont la **première option est le créateur**, puis les personnages débloqués (les verrouillés n'y figurent pas).
  - **Créateur** : paramètres dans `resources/generation.json` → `creator` : `points` 24, `base` 4, `min` 1, `max` 10 par stat. Les 6 stats démarrent à 4 (total 24) ; boutons −/+ par stat, sans jamais dépasser 24 au total. Boutons Homme/Femme (changer le sexe retire un nouveau prénom du bon sexe et ré-accorde le métier). Deux boutons de relance **sans texte, juste l'icône dé** (&#127922;) : un pour le **prénom**, un seul pour le **métier et l'âge** (tirés ensemble). Pas de liste de sélection. Visuel **compact** (portrait, prénom et métier/âge en ligne, stats sur 2 colonnes, boutons Commencer/Retour côte à côte) pour tenir sans scroll. Le choix du portrait viendra avec les images d'avatar.
  - Le personnage créé a l'id `custom`.

## Boucle narrative
- **Début** : tous sur un bateau au bout du monde → rejoindre le rivage à la nage → 1ère épreuve : les 2 premiers deviennent chefs d'équipe, répartition en 2 équipes → chaque équipe est emmenée sur une île déserte, construit un camp, vit avec très peu de moyens.
- **Phase 1 (équipes)**, boucle jusqu'à **8 éliminés** :
  - Épreuve de confort : l'équipe gagnante gagne un avantage de survie (matériel de pêche, équipement, bon repas).
  - Épreuve d'immunité : l'équipe perdante doit éliminer un des siens.
  - Conseil : chaque candidat vote pour celui qu'il veut voir sortir.
- **Réunification** (dès 8 éliminés) : une seule île, une seule équipe.
- **Phase 2 (individuelle)**, jusqu'à **5 candidats restants** :
  - Épreuve de confort : récompense individuelle.
  - Épreuve d'immunité : seul le vainqueur est immunisé au prochain conseil.
  - Conseil : un candidat éliminé.
- **Épreuve d'orientation** : seuls les 3 premiers restent.
- **Épreuve des poteaux** : le gagnant choisit parmi les 2 perdants celui qui reste en jeu.
- **Finale** : tous les éliminés depuis la réunification votent dans un dernier conseil ; le plus voté est le vainqueur.

## Éléments RPG
- Les stats des candidats influent sur leur performance aux épreuves. Toute la partie survie doit faire évoluer ces stats (hausse/baisse).
- **Épreuves** = jeux sollicitant les stats, sous forme de **succession de tests au lancer de dés**, enrobés de narration.
- Test de stat : `d20 (1–20) + stat >= seuil` (`Candidate.rollStat` / `statTest`).

## Contenu modulable : `public/content/`
Le contenu n'est **pas compilé** : il est servi tel quel et chargé par `fetch` au lancement (`src/content/ContentLoader.js`). Il est donc modifiable après build/déploiement.
```
public/content/
  manifest.json                 { start, cards: [fichiers], characters: [dossiers], resources: [noms] }
  cards/<theme>.json            { "cards": [...] }, un fichier par thème (introduction, équipes, camp)
  cards/challenges/*.json       cartes de TOUTES les épreuves (nage, parcours du feu, flambeaux, élastiques, plongée...)
  manifest.challenges           catalogue des épreuves : { id, name, description, context: TEAM | INDIVIDUAL, random, start, end }
  characters/<id>/infos.json    un dossier par personnage (futures cartes/images dans le même dossier)
  resources/<nom>.json          données de génération
```
- Un navigateur ne pouvant pas lister un dossier, **tout nouveau fichier doit être déclaré dans `manifest.json`** (l'éditeur le fait pour les cartes).
- `manifest.start` = id de la première carte d'une partie.
- Ressources de génération (`resources/`) : `generation.json` (règles : `candidateCount`, `reserveCharacterCount` = nombre de personnages de la réserve tirés par partie, âges, plage des attributs des profils générés, `creator`), `regions.json` (35 archipels, phrases complètes type « l'archipel des Marquises » → variable `{region}`), `firstnames_male.json` / `firstnames_female.json` (35 chacun), `jobs.json` (36 métiers `{m, f}`). Format : `{ "values": [...] }`.
- Règle d'âge : aléatoire 18–60 avec **au moins 2 candidats < 30** et **4 > 45** sur les 20 (seuls les profils générés sont ajustés). *(La demande initiale disait « < 3 », interprété comme < 30.)*
- Pour ajouter un personnage à la réserve : créer `characters/<id>/infos.json` (avec `rarity` et `unlockCost`) et ajouter `<id>` dans `manifest.characters`.

## Système de cartes (règles)
Le jeu est une **grande pile de cartes** qui s'adapte aux choix du joueur.

Champs d'une carte :
- `text` + `choices.left` / `choices.right` (sens du swipe). Un choix a `text`, `next`, et peut avoir des `effects` (optionnels) qui influent sur le jeu.
- `type` : comportement global de la carte.
  - `NARRATION` : classique (défaut si vide).
  - `DICE` : jet de dé. Champ `dice: { entity, stat, threshold, success, fail }` ; `entity` = `{player}`/`{interlocutor}`/nom ; `success`/`fail` = valeurs de `next`. Le `next` des choix est ignoré ; le détail du jet est dans `{lastRoll}` (ex. « SOC 9 + d20 2 = 11 / 10 »).
  - `PORTRAITS` : carte spéciale qui fait défiler les candidats un par un (0,7 s chacun, `PORTRAIT_INTERVAL_MS` dans `InGamePage.vue`), **une seule fois, sans boucle** : s'arrête sur le dernier (nom/métier/âge/compteur ; image à venir).
  - D'autres types seront ajoutés dès qu'une carte aura un comportement spécifique (afficher par `InGamePage`).
- `theme` : l'évènement narratif auquel la carte appartient (libre ; ex. `INTRODUCTION`, `EQUILIBRE_SUR_L_EAU`).
- `img` : image associée. `single_use` : si vrai, la carte ne peut être piochée qu'une fois par partie (filtre appliqué aux tirages par thème, pas aux liens `ID:` explicites).
- `name` et `text` acceptent des variables : `{player}`, `{interlocutor}`, `{region}`, `{lastRoll}` (`Game.format`).
- `next` : détermine la carte suivante.
  - `ID:intro_02` → la carte d'id donné (les ids doivent être uniques ; un doublon donne un warning au chargement).
  - vide → **autre** carte au hasard du **même thème** que la carte courante (hors `single_use` déjà jouées).
  - `THEME:<THEME>` → carte aléatoire de ce thème.
  - `TEST:{player}:STR:12:ID§0:ID§1` → stat test, génère une carte résultat intermédiaire ; réussite → carte 0, échec → carte 1. Le `§` remplace `:` dans les `next` imbriqués.
  - `END` ou aucune carte disponible → fin de la pile (`game.finished`, affiche « Fin du contenu disponible »).
- Effets (`effects: [{type, target, value, ...}]`) :
  - `ENERGY` : énergie de `target` += value (bornée 0–100).
  - `RELATION` : jauge `gauge` (`AFF` par défaut, ou `REP`) de l'opinion de `target` **envers** `about` (défaut `{player}`) += value, sans borne. Ex. `{type:"RELATION", gauge:"REP", target:"TEAM", about:"{player}", value:-1}` = le joueur rate un mouvement, ses coéquipiers l'estiment moins.
  - `SET_INTERLOCUTOR` (`target` = nom ou `RANDOM`), `ELIMINATION`.
  - `CHALLENGE_START` / `CHALLENGE_MOVE` / `CHALLENGE_END` / `CHALLENGE_CLOSE` : effets **communs à toutes les épreuves**. `target` = **identifiant de l'épreuve** (ex. `"SWIM"`) ; `params` (START) = paramètres propres à l'épreuve ; `about` (MOVE) = candidat concerné, `value` = variation du score. Le moteur ne fait que déléguer à la classe de l'épreuve (voir « Épreuves »).
- Une carte peut avoir `on_enter: [effects]` : effets appliqués dès qu'elle devient la carte courante (sans attendre le swipe). Type `CHALLENGE_TURN` : un tour d'épreuve, avec `challenge: { id, onFinish }`, résolu par `Challenge.playTurn`.
  - `target` : `{player}`, `{interlocutor}`, un nom, ou pour ENERGY/RELATION `ALL` (tous les autres candidats en jeu) / `TEAM` (coéquipiers de `about`).

### Épreuves (`src/model/challenges/`)
**Toute implémentation d'épreuve va dans `src/model/challenges/`.** Rien de spécifique à une épreuve ne doit être dans `Game.js` ni `Effect.js`.
- `Challenge.js` : classe de base (`id`, `params`, `visible`, `display`, `candidates`) avec les méthodes déléguées par le moteur : `start(game)`, `move(game, effect)`, `playTurn(game, leftOrRight, card)` (renvoie le `next`), `update`, `end(game)`, `close(game)`. Elle contient aussi les **outils réutilisables par toutes les épreuves** :
  - **`jointRoll(members, stats, threshold)`** : le **jet joint** (participants = duo, équipe… ; `stats` = une stat commune ou une stat par participant ; renvoie `{ ok, total, rolls, text }`).
  - **Étapes génériques** (`Step` : `RUN`, `HURDLE`, `JOINT_RUN`, `JOINT_OBSTACLE`) et leurs **modes** (`Mode`), résolues par `resolveSolo(step, c, side, logIf)` et `resolveJoint(step, members, side, logIf)`, avec `chooseMode` / `modeFor` / `aiMode` (swipe du joueur, IA pour les autres) et `describeStep` (textes des boutons). Leurs paramètres par défaut (`STEP_PARAMS`) sont fusionnés sous ceux de chaque épreuve.
  - Points d'accroche à fournir par l'épreuve : `advance(candidate, cells)`, `segmentRemaining(candidate)`, `partnerOf(candidate)` (`RaceChallenge` implémente les deux premiers à partir de `positions` et de `steps`). Une épreuve ajoute ses **étapes spécifiques** dans son propre fichier (ex. `FireStep` dans FireCourse).
- `index.js` : registre `identifiant → classe` + `createChallenge(id, params)`. **Pour ajouter une épreuve** : créer `challenges/MonEpreuve.js` (`extends Challenge`, `static get ID()`), l'enregistrer dans `index.js`, écrire ses cartes avec des effets `CHALLENGE_*` ayant `target: "<ID>"` et des cartes `CHALLENGE_TURN` si elle a des tours.
- `Game.challenges` = épreuves démarrées, par id ; `Game.getChallenge(id)` ; `Game.activeChallenge` = la première épreuve `visible`. Une épreuve alimente `game.vars` avec ses propres variables de texte.
- Affichage : chaque épreuve a `display` (clé du composant, `InGamePage` choisit). Seul `RACE_TRACK` (`RaceTrack.vue`) existe ; il utilise `cellLabel(i)` et `statusText` de l'épreuve.
- Épreuves existantes : `SWIM` (SwimRace), `FIRE_COURSE` (FireCourse), toutes deux basées sur `RaceChallenge` ; `TORCHES` (TorchRelay), `ELASTICS` (ElasticRace), `DIVE_RELAY` (DiveRelay), `SUNKEN_WEIGHTS` (WeightRelay), `POTTERY` (PotteryRelay), `SLING` (SlingRelay) (ces quatre-là sur `RelayRace`), `SPOOL` (SpoolRace), `DIVING_BOARD` (DivingBoard), `WATER_PUZZLE` (WaterPuzzle), épreuves d'équipe basées sur `TeamRace` (voir « Épreuves d'équipe ») ; `TEAM_DRAFT` (TeamDraft), formation des équipes ; `CAMP_LIFE` (CampLife), vie de camp et cycle jour / nuit (pas d'affichage de score : second header).
- **Collection d'épreuves et jours d'épreuve** : toutes les épreuves ont leurs cartes dans `public/content/cards/challenges/` et une entrée dans `manifest.challenges` (`context` = `TEAM` avant la réunification, `INDIVIDUAL` après ; `random: true` = dans la réserve de tirage ; `start` = première carte ; `end` = dernière carte, qui termine la partie en mode « épreuve seule »). Les **jours d'épreuve** (`challengeDays` de CAMP_LIFE) remplacent le matin : `Game.drawChallenge(contexte)` tire au hasard une épreuve `random` du bon contexte (`game.challengeContext` = TEAM tant que `game.reunified` est faux), en évitant celles déjà jouées. Mécanique de cartes : le camp renvoie `next: "CHALLENGE:<contexte>:<carte de retour>"` ; l'épreuve se termine par une carte `next: "RETURN"` qui rend la main au camp (à midi). Sans épreuve disponible dans le contexte (aucune individuelle pour l'instant), la vie de camp continue. Pas encore de calendrier : `challengeDays` est vide dans le contenu actuel. Pour ajouter une épreuve : cartes dans `cards/challenges/`, classe dans `model/challenges/` + registre, entrée de catalogue.
- **Menu DEBUG « Épreuves »** (`components/debug/ChallengeDebugPage.vue`, visible si `DEBUG` dans `src/debug.js`) : liste toutes les épreuves du catalogue et en lance une seule avec un joueur aléatoire (`randomCharacter`) et des candidats aléatoires (équipes équilibrées 5 M + 5 F avec chefs et noms pour les épreuves d'équipe : `Game` option `randomTeams`). Options de `new Game(content, player, { debug, startCard, standaloneEnd, randomTeams })` ; pas de Koh-points à la fin.
- Effets d'équipe : `TEAM_RELATION` (chaque membre modifie sa jauge envers chacun des autres, `target` = `PLAYER_TEAM` / `RED` / `YELLOW` / `ALL`) et `PICK_TEAMMATES` (tire des coéquipiers au hasard dans des variables). `getEntityByName` accepte désormais `{variable}` pour tout nom rangé dans `game.vars`.
- `Game.results[idÉpreuve]` : résultats déposés par une épreuve terminée pour les suivantes (ex. `results.FIRE_COURSE.winners`). Effet `CHALLENGE_UPDATE` : fait avancer le déroulement automatique de l'épreuve (`Challenge.update`).

Pendant une épreuve, chaque candidat a un **score d'avancement**, affiché ou non au-dessus de la zone de carte (`visible`, composant `RaceTrack.vue` = minimap avec l'avatar de chaque candidat, joueur mis en évidence, bordure de couleur d'équipe si équipe). Pour une épreuve **par équipes**, c'est le score d'équipe qui doit être affiché (non implémenté, seule la course individuelle existe).

**Épreuve de nage (bateau → rive, id `SWIM`)** — `src/model/challenges/SwimRace.js`, cartes dans `cards/epreuve_nage.json` (thème `EPREUVE_NAGE`), enchaînée après `intro_06_helico` :
- 10 cases (case 0 = bateau, 10 = rive). Paramètres surchargeables via `params` de l'effet `CHALLENGE_START` (`length`, `diveThreshold` 12, `soloThreshold` 14, `groupThreshold` 10).
- **Plongeon** (carte DICE, test d'AGI, seuil 12) : réussite = plongeon carpé, case 2 ; échec = tombe à l'eau, case 1. Les non-joueurs plongent au démarrage (même règle).
- **Chaque tour** (carte `CHALLENGE_TURN` rejouée tant que le joueur n'a pas atteint la rive ; tous les candidats agissent en même temps) :
  - gauche = **nager seul** : test de SWI (seuil plus haut) ; réussite +2 cases, échec +1.
  - droite = **nager avec les autres** : +1 case ; test de SOC : réussite → un compagnon gagne en **AFF** envers le nageur (+1) ; échec → le compagnon doit l'aider et perd en **REP** envers lui (−1).
  - Les non-joueurs choisissent seuls (plus SWI est haut, plus ils préfèrent le solo).
- **Classement** : ordre d'arrivée (égalités tirées au hasard). Quand le joueur arrive, les autres finissent la course instantanément (`finishRemaining`). Puis (effet `CHALLENGE_END` de la carte `swim_03_rive`) gain/perte de **REP** vu par tous les autres candidats : **seuls** les 1er (+5), 2e (+4), avant-dernier (−4) et dernier (−5) changent ; tout le reste du classement ne change rien (`Challenge.rankReward`, paramètre `rankRewards`, commun à toutes les épreuves à classement).
- Fin : carte de Denis Brognard qui félicite les candidats d'avoir atteint la rive (retire la minimap via `CHALLENGE_CLOSE`), puis enchaîne sur la première épreuve (ci-dessous).

**Première épreuve : parcours et feu (id `FIRE_COURSE`)** — `src/model/challenges/FireCourse.js`, cartes dans `cards/epreuve_feu.json` (thème `EPREUVE_FEU`). Denis accueille (« L'aventure a déjà commencé pour vous… »), explique (parcours, obstacles, feu à allumer avec un silex, binômes), lance le top départ, puis cartes `CHALLENGE_TURN` jusqu'à ce que le duo du joueur ait allumé le feu.
- Parcours de **13 cases** (`STEPS`, position = cases franchies) : 2 course `RUN` (STR, seuil 8) · 2 haies `HURDLE` (AGI) · 1 case **couleur** · 4 course en **jet joint** `JOINT_RUN` (STR, 25) · 1 obstacle en jet joint `JOINT_OBSTACLE` (courte échelle, ci-dessous) · 2 course en jet joint `JOINT_RUN` · 1 case **feu** (INT). Les étapes RUN, HURDLE, JOINT_RUN et JOINT_OBSTACLE sont **génériques** (dans `Challenge`) ; seules **COLOR** (tirage des binômes) et **FIRE** sont spécifiques à `FireCourse` (`FireStep`).
- **Choix au swipe sur les courses** (`RUN` / `JOINT_RUN`) — gauche : **course modérée**, +1 case ; en cas d'échec on n'avance pas et on perd 1 REP auprès de son binôme (en jet joint, les deux binômes perdent 1 REP l'un envers l'autre). Droite : **sprint**, coûte **3 énergie au total** (jet de STR inclus), +2 cases (sans sortir de la série de cases de même type) ; en cas d'échec on avance quand même d'1 case. En jet joint, c'est le swipe du joueur qui choisit pour son duo.
- **Obstacle : la courte échelle** (`JOINT_OBSTACLE`, jet joint, seuil 27) — celui qui **monte** fait un jet d'**AGI**, celui qui **porte** un jet de **STR** (le porteur paie donc 1 énergie). **Swipe gauche** : le joueur est **au-dessus** (AGI) ; **swipe droite** : il est **en dessous** (STR) ; son binôme prend l'autre rôle. Pour un duo sans joueur, celui qui a le meilleur écart AGI − STR monte. Réussite : le duo avance d'une case. **Échec : pas d'avance et −1 REP entre les deux membres** (dans les deux sens, `ladderFailRep`).
- **Haies** — gauche : **enjamber**, seuil très bas (4), coûte 1 énergie. Droite : **sauter**, seuil plus haut (12), 0 énergie, **+1 REP auprès de tous les autres** si réussi. Dans les deux cas un échec laisse devant la haie.
- Les non-joueurs choisissent seuls (les costauds sprintent si leur énergie > 10, les agiles sautent). Les gains/pertes de REP ne sont jamais montrés au joueur (les boutons et textes ne font que suggérer : « impressionne », « soupire »).
- **Énergie** : tout jet de STR ou de SWI coûte **1 énergie** (`Candidate.rollStat`, partout dans le jeu, chaque membre d'un jet joint paie son jet) ; l'énergie est bornée à 0 (pas d'interdiction d'agir à 0 pour l'instant).
- **Couleurs** : chacun pioche une couleur parmi 10 (`COLORS`, tons **pastel** : orange, vert, violet, bleu, blanc, noir, rouge, jaune, turquoise, rose), jamais une déjà prise par quelqu'un du même sexe. La couleur piochée devient la **bordure de l'avatar** du candidat sur la minimap (`avatarBorder`, 2 px) et la bordure du bandeau de statut du joueur (`statusColor`). Si quelqu'un (forcément de l'autre sexe) attend avec cette couleur → **duo mixte** formé, ils continuent côte à côte ; sinon le candidat attend sur la case. Avec autant d'hommes que de femmes, tout le monde finit apparié. Le joueur voit « En duo avec X » (ou « En attente d'un binôme ») sous la minimap (`challenge.statusText`).
- **Jet joint** (`Challenge.jointRoll`) : chaque membre du duo lance d20 + stat, les totaux sont **additionnés** et comparés à un seuil élevé (un partenaire catastrophique fait presque toujours échouer). Réutilisable pour tout groupe (duo, équipe).
- **Feu** : le duo doit réussir **3 jets joints d'INT consécutifs** (seuil 25 ; un échec remet à 0), les deux doivent être présents sur la case. Les premiers duos à y arriver gagnent.
- **Conséquences** (`end`) : chaque duo +3 AFF envers son binôme (des deux côtés, réussite collective) ; REP auprès de tous les autres selon le classement des duos, **1er duo +5, 2e +4, avant-dernier −4, dernier −5** (les autres duos : rien) ; le **dernier duo** reçoit en plus `Candidate.councilVotes += 1` (un vote à leur nom inscrit pour le prochain conseil auquel ils assisteront ; les conseils ne sont pas encore implémentés).
- Variables de texte : `{raceLog}`, `{nextStep}`, `{stepActionLeft}` / `{stepActionRight}` (texte des boutons de swipe, mis à jour à chaque tour), `{playerRankLabel}` (rang du duo du joueur), `{raceWinners}`, `{raceLosers}`.
- Tous les seuils/récompenses sont dans `DEFAULT_PARAMS` et surchargeables via `params` de `CHALLENGE_START`. Durée de l'épreuve observée pour le joueur : ~17 swipes en moyenne (11 à 33+ si le binôme arrive tard).
- Les deux vainqueurs deviennent chefs d'équipe (voir ci-dessous). `FireCourse.end` dépose `game.results.FIRE_COURSE = { winners, losers, duos }`.

**Formation des équipes (id `TEAM_DRAFT`)** — `src/model/challenges/TeamDraft.js`, cartes dans `cards/equipes.json` (thème `FORMATION_EQUIPES`), enchaînée après la carte finale de la FireCourse :
- Le duo gagnant **se sépare** : chacun devient chef d'une équipe différente, **Rouge ou Jaune** (couleur tirée au hasard). Cartes : Denis annonce les chefs → explique la règle → tours de choix → Denis remet la bannière à chaque chef (« Les Rouges, vous êtes l'équipe des {Nom} ! ») → fin.
- Les chefs choisissent **à tour de rôle, la cheffe (femme) en premier**. Chaque chef **alterne les sexes en commençant par le sexe opposé au sien** → chaque équipe finit à 10 : 5 hommes + 5 femmes.
- Chef non-joueur : décision **collective** de son équipe (voir « Décisions », contexte positif). Chef joueur : il **clique sur le portrait** voulu (`DraftPicker.vue`, portraits de tous les candidats ; seuls les libres du bon sexe sont cliquables ; les choisis ont la bordure de leur équipe ; couronne sur les chefs), **puis swipe pour valider** ; swiper sans sélection n'avance pas. Le joueur non chef : un swipe = un choix par chef (il est choisi comme les autres).
- Noms tribaux aléatoires : `resources/team_names.json` (35 noms inventés). Variables de texte : `{chiefRed}`, `{chiefYellow}`, `{firstChief}`, `{draftLog}`, `{draftPrompt}`, `{draftAction}`, `{teamRedName}`, `{teamYellowName}`, `{playerTeamText}`.
- Le header affiche « Équipe rouge · {nom} » une fois les équipes nommées.
- **Relations de la formation** (échelle de référence ; `TeamDraft.applyPickRelations`, historique `TEAM_SELECTION`) : le **1er** équipier choisi par un chef gagne **+3 AFF envers lui** (c'est son AFF envers le chef qui monte) et **+2 REP auprès de tout le monde** ; le **2e** +2 AFF ; les suivants +1 AFF **sauf le dernier** de l'équipe (rien) ; le **dernier homme** et la **dernière femme** choisis subissent **−2 REP auprès de tout le monde**. À la fin, **tous les membres d'une équipe gagnent +1 AFF envers chacun des autres** (effet `TEAM_RELATION`). Les choix précédents influencent les suivants (la REP gagnée par le 1er choisi se retrouve dans les décisions de l'autre chef).
- Ajoute les variables `{playerTeamLabel}` (Rouges / Jaunes) et `{playerTeamName}` (nom tribal).
- `RaceChallenge.js` : base commune des épreuves de course (positions, arrivées, minimap `cellLabel`, `statusText`) dont héritent `SwimRace` et `FireCourse`.
- Variables de texte : `{raceLog}` (compte rendu du tour du joueur), `{playerRankLabel}`, `{raceWinner}`.
- Attention : le seuil du plongeon est dupliqué entre `dice.threshold` de `swim_01_saut` et `diveThreshold` (à garder identiques).

- **Bande de validation** : quand le swipe est assez avancé pour passer à la carte suivante (déplacement > 200 px, `commitSide`), une **bande verticale de 14 px collée au bord de l'écran** (côté du swipe) apparaît, de la couleur du choix (gauche jungle, droite mer) ou **blanche** quand le swipe n'est pas une décision.
- Les textes des choix (gauche/droite) sont des **boutons toujours visibles sous la carte** (gauche jungle, droite mer) ; toucher un bouton = swiper ; pendant le swipe, le bouton du côté visé se met en avant.
- Le header (`GameTopBar`) affiche jour, période, équipe (« Sans équipe » au départ), jauge d'énergie du joueur, et le médaillon du joueur qui ouvre `CandidateListModal` : liste compacte de tous les candidats (avatar, nom, métier, âge), **triée selon les relations du joueur** (voir « Décisions ») ; bordure d'avatar de la couleur d'équipe (`TeamCssColor`) uniquement si le candidat a une équipe ; éliminés grisés. Aucune jauge AFF/REP affichée.

## Architecture du code (état actuel, WIP)
- `src/model/` : `Character.js` (Character, Candidate, Attribute), `CandidateGenerator.js` (casting + quotas d'âge), `Card.js` (CardType NARRATION/DICE/PORTRAITS/CHALLENGE_TURN), `challenges/` (épreuves, voir ci-dessus), `Game.js` (`new Game(content, playerCharacter)`, `next()`, `getNextCard()`, `applyEffect()`, `rollDice()`, `format()`), `Effect.js`, `Team.js`, `Condition.js`, `GameHistory.js`, `Decision.js`.
- `src/content/` : `ContentLoader.js` (fetch du manifest/cartes/catalogue d'épreuves/personnages/ressources), `ContentStore.js` (écriture, éditeur : réécrit chaque thème **au même chemin que celui d'où il a été lu**, donc les épreuves restent dans `cards/challenges/`, et conserve les autres clés du manifest dont `challenges`).
- `src/components/` : `mainMenu`, `charSelection` (props `characters`, `resources`, `profile`), `charGallery`, `game` (InGamePage, GameTopBar), `editor`.
- `src/pages/IndexPage.vue` : charge le contenu, puis menu → sélection → partie. `src/router/routes.js` : `/` jeu, `/editor` éditeur.
- Tests rapides : la logique de `Game`/générateur a été validée par une simulation Node (300 parties) bundlée avec esbuild (hors repo).
